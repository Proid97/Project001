# 왁스팝 개발·최적화 계획

작성·갱신: 2026-10-15. 상태: 구현 전 권장안. 세 차례 자체 검토를 반영했습니다. 성능 수치와 일정은 아직 실측하지 않았습니다.

먼저 읽을 문서: [대화맥락](01_대화맥락.md), [게임기획](10_게임기획.md), [플레이 영상 분석](14_플레이영상분석.md).

## 1. 이번에 정리한 방향

3D로 볼의 모양·재질·빛을 맞춘 뒤 2D 이미지로 출력하는 방식을 권합니다. 게임에서는 그 이미지를 재사용하고, 눌림·늘어남·착지는 코드로 움직입니다. 껍질 파열은 짧은 이미지 묶음과 작은 파편을 함께 씁니다.

3D로 제작했다고 자동으로 가벼워지지는 않습니다. 게임에 넣는 이미지의 크기·장수·겹침과 화면 해상도가 실제 비용을 결정합니다. 모든 손가락 방향과 변형을 미리 렌더링하면 오히려 이미지가 지나치게 많아집니다. 원본 제작 시간도 별도 비용입니다.

개발은 볼 하나 → 작은 보드 → 7×8 한 판 → 특수 볼 → 12단계 순서로 진행합니다. 먼저 손맛과 규칙을 확인하고 화면을 넓힙니다.

### Ponytail 적용

사용자가 알려준 [ponytail.dev](https://ponytail.dev/)에서 공식 저장소로 이동해 실제 [SKILL.md](https://github.com/DietrichGebert/ponytail/blob/84740e3d344b69b4a133201fa519eb37a62a2b2a/skills/ponytail/SKILL.md)를 읽었습니다. 확인한 커밋은 `84740e3d344b69b4a133201fa519eb37a62a2b2a`, 라이선스는 MIT입니다. 기본 `full` 지침을 이번 계획에 적용합니다. 앱 전체에 플러그인이나 자동 실행 훅을 설치한 상태는 아닙니다.

| 지침을 적용할 곳 | 이번 작업 방식 |
| --- | --- |
| 필요한 일부터 확인 | 한 판의 연결·파열·목표에 필요한 것부터 구현 |
| 기존 기능 재사용 | 브라우저 저장·표준 버튼·엔진의 입력·이미지 묶음·Tween부터 사용 |
| 새 코드 줄이기 | 같은 계산을 여러 곳에 복사하지 않고 짧고 읽히는 함수로 유지 |
| 과한 구조 피하기 | 미리 만든 범용 시스템·불필요한 파일 분할·수많은 선택 옵션을 두지 않음 |
| 중요한 검사 유지 | 경계 규칙·중복 집계·저장 오류·실기기 확인을 생략하지 않음 |

초기 파일 수와 의존성을 줄이는 기준이며, 런타임 성능 보장은 아닙니다. 사이트의 코드량·비용 절감 수치를 왁스팝의 예상 성능으로 옮기지 않습니다. 한계가 있는 임시 코드는 바꿔야 할 조건과 함께 표시합니다.

## 2. 유지할 게임 규칙과 아직 열린 선택

| 구분 | 내용 |
| --- | --- |
| 현재 규칙 | 세로·7×8·4색·대각선 포함 같은 색 3개 이상 연결 |
| 입력 | 같은 볼 재사용 금지, 바로 전 볼로 돌아가면 마지막 선택 취소 |
| 취소 | 3개 미만·입력 끊김은 취소하고 횟수를 쓰지 않음 |
| 정산 | 유효 연결 한 번에 횟수 1, 선택 순서 파열, 낙하·보충 뒤 자동 소거 없음 |
| 크런치볼 | 일반 볼 6개 이상이면 마지막 칸에 생성. 다음 연결에서 3×3 파열·기존 특수 볼 연쇄 |
| 중복 방지 | 같은 칸·볼·목표를 한 행동에서 중복 집계하지 않음. 특수 볼 포함 연결은 새 특수 볼을 만들지 않음 |
| 종료 | 마지막 목표를 채우면 횟수 0이어도 성공. 연결 불가면 무료 섞기 후 다시 확인 |
| 아직 제안 | 마지막 일반 볼을 수집한 것으로 세면서 크런치볼을 남길지, 첫 왁스판을 모두 1겹으로 할지 |
| 이번 기술 제안 | 웹 우선 시제품, 아래 엔진·성능 예산·에셋 규격·일정 |

게임기획에 남아 있는 미확정 집계 방식은 규칙 파일의 이름 있는 값으로 표시합니다. 범용 설정 시스템까지 만들지 않습니다. 임시 시제품은 사용한 값을 화면·검증 기록에 표시합니다. 정식 12단계 수치를 조정하기 전에 이 값을 결정해야 합니다. 사용자 승인 없이 확정 규칙으로 바꾸지 않습니다.

## 3. 실행 환경과 기술 선택

먼저 iPad·휴대폰 브라우저에서 손맛을 비교하는 웹 시제품을 권합니다. 앱스토어 출시 방식과 네이티브 엔진은 이 단계의 완료 조건에 넣지 않습니다.

| 선택 | 이번 계획 |
| --- | --- |
| 언어 | TypeScript. 규칙에 쓰는 값과 이벤트의 모양을 명확히 정의 |
| 엔진 | Phaser 4.2.1을 우선 검토. 2026-10-15 공식 안정판 페이지에서 확인한 버전 |
| 빌드 | Vite 기반 로컬 빌드. 실제 착수 시 도구 호환성을 확인하고 정확한 버전·잠금 파일 저장 |
| 그림 | WebGL 2D 스프라이트. 첫 시제품은 위치·회전·확대 변형부터 구현 |
| 소리 | 엔진의 Web Audio 경로와 공통 믹서. 원음과 게임용 가공본 분리 |
| 화면 | 게임은 Canvas, 설정·결과·접근성 안내는 필요한 만큼 HTML 버튼·텍스트 사용 |
| 물리 | 격자 계산과 짧은 보간. 실시간 강체·젤리·유체 시뮬레이션은 초기 범위 밖 |

Phaser는 입력·장면·이미지 묶음·시간 조절 기능을 함께 제공해 첫 개발을 줄일 수 있다는 판단입니다. 다른 엔진보다 반드시 작거나 빠르다는 측정 결과는 아닙니다. 4.x는 렌더러가 바뀌었으므로 3.x 예제의 셰이더·Mesh 코드를 그대로 가져오지 않습니다.

착수 직후 56개 볼·터치·음원·화면 크기 변경만 있는 작은 성능 시제품을 만듭니다. 사용자 기기에서 적합한지 보고 엔진을 고정합니다. 이 시험이 실패하면 원인을 먼저 좁히고 렌더러나 엔진 변경을 검토합니다.

작업 소스는 여러 파일로 관리합니다. 공유용 플레이 시제품은 JS·이미지·소리를 넣은 단일 HTML로 별도 묶습니다. 개발 코드 전체를 한 HTML에 작성할 필요는 없습니다. 기존 `waxpop-review.html`은 조사 검토본으로 유지하고 플레이 시제품과 구분합니다.

### 3-1. 라이브러리·도구를 쓸 곳

같은 일을 잘 해주는 기능은 적극 재사용합니다. 개발 도구의 개수와 게임에 함께 실리는 의존성은 구분합니다. 아래는 도입 계획이며 아직 게임용 패키지를 설치한 목록이 아닙니다.

| 도구 | 도입 시점 | 줄일 직접 작업 | 실행 파일 포함 |
| --- | --- | --- | --- |
| Phaser | 첫 시제품 | 입력·장면·Tween·이미지 시퀀스·파티클·텍스처·오디오·시드 난수 | 포함 |
| TypeScript + Vite | 첫 시제품 | 타입 검사·개발 중 자동 갱신·빌드·에셋 경로 처리 | 개발 도구 자체는 제외 |
| Vitest | 첫 규칙 코드 | 고정 보드·오류 재현·회귀 검사 | 제외 |
| Playwright Test | 첫 실행 화면 | 브라우저 조작·화면 크기·오프라인·콘솔·저장·음원 검사 | 제외 |
| Biome | 첫 소스 작성 | 코드 정돈·기본 오류 검사. 포매터와 린터 설정을 한곳에서 관리 | 제외 |
| vite-plugin-singlefile | 첫 공유용 HTML | 빌드된 JS·CSS 합치기. 이미지·음원 포함 여부는 별도 검사 | 플러그인 자체는 제외 |
| Blender | 첫 볼 제작 | 같은 모델·빛으로 상태와 색 출력 | 제외 |
| Pillow·FFmpeg | 첫 에셋 가공 | 이미지 크기·여백·메타데이터, 음원 자르기·변환·검사 | 제외 |

엔진 기본 Tween과 파티클 재사용 기능을 먼저 씁니다. 파편마다 별도 객체 풀을 새로 만들지 않습니다. 난수도 Phaser의 `RandomDataGenerator`를 사용하고 저장·복원 기능을 재사용합니다. 규칙에는 필요한 난수 함수만 인자로 넘겨 엔진을 직접 불러오지 않게 합니다. 보드용과 장식용 인스턴스는 분리합니다.

별도 GSAP·Howler·물리 엔진·상태 관리·UI 프레임워크는 엔진과 기능이 겹치는지 먼저 봅니다. 지금 필요한 일을 기본 기능으로 해결할 수 있으면 추가하지 않습니다. 반대로 규칙 검사·브라우저 검사처럼 반복 작업을 줄이는 개발 도구는 실행 파일을 키우지 않으므로 필요한 시점에 도입합니다.

처음에는 크기가 같은 볼·파열 이미지를 균일한 스프라이트시트로 출력하고 Phaser가 읽게 합니다. 빈 공간이 실제 메모리 문제로 확인되면 검증된 아틀라스 도구를 도입합니다. 직접 복잡한 패킹 알고리즘을 만들거나, 처음부터 유료 도구를 전제하지 않습니다. 기존 Pillow·FFmpeg 처리도 재사용합니다.

착수할 때 Node의 지원 중인 LTS와 패키지의 지원 범위를 확인합니다. 설치한 정확한 버전·잠금 파일·직접 의존성의 용도와 라이선스를 저장하고 `npm ci`로 같은 환경을 재현합니다. 문서의 최신 버전과 패키지 설치 가능 여부를 같은 사실로 취급하지 않습니다.

### 3-2. 개발·검사 환경의 구성

처음 게임 소스를 만들 때 아래 명령과 설정을 함께 구성합니다. 지금 실행할 수 있는 게임 프로젝트가 만들어졌다는 뜻은 아닙니다.

| 개발 중 할 일 | 준비할 명령·설정 |
| --- | --- |
| 즉시 확인 | `dev`: Vite. 소스가 바뀌면 자동 갱신. 엔진을 다시 만들 때 이전 인스턴스·소리·리스너 정리 |
| 코드 정돈 | `lint`: Biome 검사. 저장 시 정돈은 해당 도구 하나에 맡김 |
| 타입 검사 | `typecheck`: `tsc --noEmit`. Vite 빌드·Vitest 실행과 별도로 수행 |
| 규칙 검사 | `test`: Vitest 한 번 실행. 작업 중에는 관련 검사만 감시 모드로 실행 |
| 실행 확인 | `test:e2e`: Playwright. Chromium과 WebKit을 구분하고 실제 iPad 결과와도 구분 |
| 웹 배포 묶음 | `build`: 일반 Vite 빌드. 파일을 나눠 캐시할 수 있게 함 |
| 개인 검토 묶음 | `build:offline`: 별도 모드의 단일 HTML 빌드. 에셋 포함·외부 요청0개 검사 |
| 공통 검사 | `check`: 코드 정돈 검사→타입→규칙→빌드. 재실행으로 실패를 숨기지 않음 |

GitHub 자동 검사는 첫 게임 소스와 함께 연결합니다. 매 변경에는 공통 검사를 돌리고, 화면·입력·에셋·저장 경로가 바뀌면 관련 브라우저 검사를 추가합니다. 공유용 파일을 만들 때는 전체 오프라인 검사를 수행합니다. 아직 없는 게임 코드를 대상으로 빈 검사를 통과시키지 않습니다.

Node24 LTS 계열을 첫 기준으로 검토합니다. 이번 환경의 Node24.19.0과 패키지 메타데이터의 지원 범위를 확인했지만 설치·실행 호환성까지 통과한 것은 아닙니다. 브라우저 검사는 처음에는 작업자1개로 시작하고, 테스트 감시·3D 렌더링·성능 측정을 동시에 돌려 서로의 결과를 흐리지 않게 합니다.

현재 Pillow와 FFmpeg 실행 경로는 확인했습니다. Blender 실행 파일은 찾지 못했으므로 실제 3D 제작 전 설치·출력 환경을 준비해야 합니다. 이 준비가 끝나기 전에는 Blender 렌더링이 가능하다고 쓰지 않습니다.

### 3-3. 단일 HTML의 이미지·소리 누락 막기

공유용 HTML과 웹 배포용 빌드는 같은 소스에서 따로 만듭니다. 단일 파일 플러그인은 JS·CSS 합치기를 맡고, 볼·파열·음원·글꼴·아틀라스 정보는 Vite가 추적하는 import로 연결합니다. 코드 안에 파일 경로 문자열만 적거나 `public/`에 둔 파일이 자동 내장된다고 가정하지 않습니다.

첫 공유 시험부터 작은 실제 이미지·짧은 음원·아틀라스 정보를 넣습니다. 오프라인 모드에서 인라인 데이터가 만들어지고 Phaser 로더가 이를 해독하는지 확인합니다. 플러그인만 설치하고 그림·소리가 없는 빈 HTML을 성공 기준으로 삼지 않습니다.

완성된 HTML을 원래 에셋 폴더와 떨어진 곳에서 열고 네트워크를 끊습니다. 외부 리소스 요청0개, 이미지 해독, 버튼으로 시작한 음원 재생, 메뉴 전환·중단·복귀를 검사합니다. 시스템 글꼴을 쓸지 허가된 글꼴을 내장할지도 명확히 합니다. 클릭할 때만 여는 출처 링크는 리소스 요청과 구분합니다.

## 4. 아트 제작과 출력 규격

### 4-1. 제작 순서

1. Blender에서 기본 볼 하나를 만듭니다. 얇고 뽀얀 껍질과 투명한 속을 따로 둡니다.
2. 정면에 가까운 고정 카메라·왼쪽 위 조명·색 관리·출력 배율을 고정합니다. 직교 카메라를 우선 비교합니다.
3. 온전한 볼, 금이 시작된 볼, 껍질이 벌어진 볼, 드러난 속을 만듭니다. 날카로운 유리 파편처럼 보이지 않게 얇고 작은 껍질 조각을 시험합니다.
4. 민트·복숭아·연보라·크림 4색을 같은 모델로 출력합니다. 색별 표면 무늬도 유지합니다.
5. 투명 배경 PNG 원본을 보존하고, 게임용은 잘라서 이미지 묶음인 아틀라스로 만듭니다.
6. 검정·흰색·실제 게임 배경 위에 올려 투명 테두리, 밝은 테두리 번짐, 속의 색을 확인합니다.
7. 실제 셀 크기로 축소해 비교합니다. 큰 원본에서만 좋아 보이는 디테일은 줄입니다.

투명한 속은 렌더링 배경에 따라 느낌이 달라질 수 있습니다. 배경까지 굳혀 넣은 이미지를 투명한 젤리로 취급하지 않습니다. 게임 배경 위 합성을 먼저 확인하고, 실시간 굴절 효과는 이 결과로 부족할 때만 검토합니다.

### 4-2. 게임에서 저장할 것과 움직일 것

| 요소 | 초기 구현 | 이유·주의 |
| --- | --- | --- |
| 일반 볼 | 색별 기본 이미지 1장씩 공유 | 56개 객체가 같은 텍스처를 재사용 |
| 눌림·착지 | 가로·세로 크기와 위치를 짧게 변형 | 프레임별 그림을 늘리지 않고 빠르게 수정 |
| 손가락 쪽 늘어남 | 방향·변형량을 제한한 이미지 변형부터 비교 | 전체가 고무처럼 늘어나 껍질 느낌을 잃지 않는지 확인 |
| 더 정교한 국소 눌림 | 선택된 볼만 작은 격자 Mesh로 변형하는 후속안 | 엔진 4.x 지원과 비용을 별도 확인. 56개에 일괄 적용하지 않음 |
| 껍질 파열 | 우선 6~10프레임의 짧은 시퀀스, 4색 같은 시간표 | 프레임 수는 축소 화면의 선명도와 메모리로 결정 |
| 파편 | 2~4종 이미지를 회전·이동·투명도 변화로 재사용 | 색·모양 변주를 이미지 장수 대신 작은 값으로 처리 |
| 속의 출렁임 | 별도 속 이미지의 크기·위치 보간 | 기본 변형으로 부족할 때만 짧은 추가 시퀀스 |
| 크런치볼 | 기본 볼 위 균열·표식 레이어 | 모든 상태를 새 볼 이미지로 복제하지 않음 |
| 그림자 | 작은 타원 이미지 공유 | 각 볼의 실시간 그림자 계산을 줄임 |
| 버튼·팝업 | 공통 패널·아이콘·실제 글자 | 15장 목업 전체를 게임 화면 이미지로 쓰지 않음 |

회전할 파편에는 방향성이 강한 빛을 과하게 굽지 않습니다. 기본 볼은 같은 조명을 유지하고 크게 회전시키지 않습니다. 한 장을 단순 색칠해 4색을 만들면 속과 껍질 색이 함께 틀어질 수 있어, 첫 출력은 4색을 따로 비교합니다.

### 4-3. 크기와 파일 관리의 첫 기준

- 볼은 128×128과 192×192 출력부터 실제 셀 크기에서 비교합니다. 모든 볼을 512×512로 저장하지 않습니다.
- 기본 아틀라스는 최대 2048×2048부터 시작합니다. UI·볼·파열의 사용 시점을 보고 최대 2장 안에서 먼저 구성합니다.
- 이미지 사이에는 여백과 가장자리 색 확장을 넣습니다. 투명 영역은 자르되 기준점과 원래 크기를 메타데이터에 남겨 파열 중 볼이 튀지 않게 합니다.
- PNG와 알파 WebP는 다운로드 크기·해독 시간·테두리 품질을 비교해 선택합니다. WebP를 썼다고 GPU 메모리가 줄었다고 쓰지 않습니다.
- 원본 `.blend`·PNG, 게임용 아틀라스, 라이선스·출력 설정을 분리합니다. 커진 원본은 일반 Git에 무작정 넣지 않고 LFS 지원·저장 한도를 확인합니다.
- 자료 조사 사진과 생성 목업은 게임 런타임 묶음에서 제외합니다. 게임용 에셋은 사용 권리가 확인된 것만 포함합니다.

## 5. 성능 예산 — 측정 전 임시 목표

| 항목 | 첫 목표 | 넘었을 때 먼저 할 일 |
| --- | --- | --- |
| 화면 갱신 | 기준 실기기 60fps, 한 프레임 약 16.7ms | CPU 작업·GPU 그리기·로딩을 구분해 원인 확인 |
| 입력 반응 | 다음 화면 갱신부터 선택을 표시 | 이미지·음원 해독을 입력 시점에서 제거 |
| 해상도 | 내부 DPR 상한 2부터 비교, 낮은 품질은 1.5 후보 | 글자·볼 선명도를 확인하며 내부 해상도 조정 |
| 장식 파편 | 화면 전체 활성 파편 80개 이내부터 시작 | 파편·섬광·잔흔을 먼저 줄임 |
| 동시 소리 | 짧은 효과음 최대 8개부터 비교 | 같은 순간의 작은 파열을 묶고 중요한 소리를 우선 |
| GPU 텍스처 | 기본 계산 48MiB 이하, 일시 전환 64MiB 이하 후보 | 프레임 수·면적·불필요한 상주 텍스처 확인 |
| 해독된 짧은 효과음 | 8MiB 이하 후보 | 긴 무음·불필요한 스테레오·미사용 후보 제거 |
| 전달 크기 | 첫 플레이 묶음 5~10MB 목표 | 아트·음원·엔진 코드별 실제 크기를 기록 |
| 반복 안정성 | 20판·설정창 반복 뒤 객체·텍스처·리스너 수가 계속 늘지 않음 | 장면 종료 정리와 예약된 작업 취소 확인 |

60fps는 실기기에서 확인할 목표입니다. 해상도나 장식 효과를 낮춰도 규칙·선택 경로·목표 반영은 같아야 합니다. 30fps 품질 모드는 60fps 유지가 어려운 기기에서 비교할 후속안입니다.

메모리는 파일 용량과 다릅니다. 아래는 압축되지 않은 RGBA8 이미지의 기본 계산이며, 밉맵·복사본·프레임버퍼·브라우저 자체 메모리는 별도입니다.

- 2048×2048×4바이트 = **16MiB**. 같은 이미지로 볼 56개를 그려도 텍스처를 56번 저장하는 구조는 아닙니다.
- 256×256×4바이트×24프레임×4색 = **24MiB**. 128×128이면 같은 조건에서 **6MiB**입니다. 실제 아틀라스는 빈 공간 때문에 더 클 수 있습니다.
- 44.1kHz·모노·총 20초의 Float32 효과음 = 약 **3.36MiB**. 스테레오는 약 두 배이며 실제 AudioContext가 다른 샘플레이트로 해독하면 다시 계산합니다.
- Base64는 원본 바이트보다 대략 4/3 크기가 됩니다. 단일 HTML의 전송 크기와 해독 후 메모리를 따로 기록합니다.

전체 탭 메모리 상한을 브라우저마다 같은 숫자로 보장하지 않습니다. 측정 가능한 텍스처·음원·객체 수를 관리하고 Safari 실기기에서 재로딩·멈춤 여부도 확인합니다. GPU 압축 형식은 지원 확인과 변환 비용이 있으므로 첫 최적화로 넣지 않습니다.

## 6. 코드 구조

처음에는 아래 정도로 시작합니다. 파일이 읽기 어려워지거나 역할이 실제로 갈릴 때 나눕니다. 거대한 공통 프레임워크·ECS·별도 서버는 만들지 않습니다.

| 경로 제안 | 맡을 일 |
| --- | --- |
| `game/src/main.ts` | 시작·엔진 설정·화면 크기·중단·저장 연결 |
| `game/src/core.ts` | 타입·경로·행동 정산·특수 볼·낙하·난수·종료·섞기. 기능별 짧은 함수 |
| `game/src/scene.ts` | 보드·입력·HUD·눌림·파열·낙하 표시 |
| `game/src/audio.ts` | 소리 선택·겹침 제한·공통 음량·중지 |
| `game/src/stages.ts` | 12단계 목표·횟수·바닥·초기 배치 |
| `game/tests/core.test.ts` | 규칙과 상태 전환의 중요한 경계 사례 |
| `art/source/`, `game/assets/`, `tools/` | 제작 원본·실행용 자료·에셋 변환 도구 |

규칙 코드는 Phaser·DOM·소리·프레임 속도에 의존하지 않게 합니다. 보드 상태와 입력을 받으면 다음 상태와 연출 목록을 돌려줍니다. 실제 게임 결과를 Tween 완료 콜백 안에서 계산하지 않습니다.

볼에는 이동해도 바뀌지 않는 ID를 주고, 바닥은 칸 번호에 붙입니다. 볼을 제거한 집합과 바닥을 처리한 집합을 따로 둡니다. 바닥 처리의 중복 제거를 볼 ID만으로 하면 안 됩니다.

칸은 56개뿐이므로 단순 배열과 작은 반복문으로 충분합니다. JavaScript 비트 연산은 32비트이므로 `1 << 칸번호`로 56칸을 한 정수에 넣지 않습니다. 처음에는 `Uint8Array(56)` 같은 표시 배열을 씁니다. 매 프레임 복잡한 탐색을 돌리지 않습니다.

### 6-1. 입력의 처리

`대기 → 연결 중 → 결과 처리 → 낙하·보충 → 대기/종료` 상태를 명확히 둡니다. 처리 중의 새 입력은 받지 않습니다.

- 첫 손가락 하나의 ID를 잡고 두 번째 손가락이 경로를 바꾸지 못하게 합니다.
- 화면 좌표를 보드 좌표로 한 번 바꾸고 근처 칸을 검사합니다. 픽셀 색을 읽거나 56개 볼의 정밀 충돌을 매번 검사하지 않습니다.
- 빠른 드래그는 이전 위치와 현재 위치 사이 구간도 검사합니다. 순서대로 지난 칸 중 인접·같은 색 조건을 통과한 것만 잇습니다. 빠르다고 중간 칸을 무조건 자동 선택하지 않습니다.
- 마지막에서 두 번째 볼로 돌아갔을 때만 마지막 선택을 뺍니다. 다른 과거 볼로 건너뛰어 경로를 지우지 않습니다.
- 포인터 취소·초점 상실·앱 전환·화면 재배치는 연결을 취소합니다. 연결 단계에서는 횟수를 차감하지 않습니다.
- 일반적인 포인터 놓기와 브라우저가 보내는 입력 취소를 구분합니다. 보드 밖으로 움직이거나 놓는 경우도 실제 터치 기기에서 시험합니다.
- 엔진의 입력 경로 하나를 사용합니다. 같은 동작을 Phaser 이벤트와 DOM 이벤트 양쪽에서 처리하지 않습니다. 영역 밖 놓기 전달이 부족할 때만 포인터 캡처를 연결하고, 중단·취소 처리는 한 함수로 모읍니다.
- 브라우저 스크롤 방지는 게임 조작 영역에만 적용합니다. 설정창과 문서의 스크롤을 함께 막지 않습니다.

### 6-2. 유효 행동 한 번의 처리

1. 경로를 규칙 코드에서 다시 검사합니다. 유효하면 행동 ID를 하나 만들고 횟수를 정확히 1 차감합니다.
2. 제거할 볼과 발동할 기존 크런치볼을 모읍니다. 새로 발견한 크런치볼은 대기열에 넣고 한 번씩만 처리합니다. 범위는 보드 안쪽으로 자릅니다.
3. 볼 수집·왁스판·특수 볼 생성을 각각 계산합니다. 범위가 겹쳐도 같은 대상을 다시 세지 않습니다. 크런치볼 포함 연결이면 생성을 막습니다.
4. 결과 보드를 만들고 칸 아래부터 압축해 낙하량을 계산합니다. 빈칸만 난수로 채웁니다. 새 매치를 찾아 자동 소거하는 단계는 없습니다.
5. **목표 완료를 먼저 확인**하고, 그다음 남은 횟수로 실패를 판정합니다. 계속할 수 있을 때만 연결 가능 여부를 확인합니다.
6. 연결이 없으면 보드용 난수의 `shuffle`로 한 번 섞고 다시 검사합니다. 여전히 없으면 같은 색 볼 3개를 이웃한 3칸에 놓고 나머지를 섞습니다. 볼 ID·색·특수 볼 개수와 바닥은 보존하고 횟수는 차감하지 않습니다. 마지막으로 연결 가능 여부를 다시 확인합니다.
7. 선택 순서 파열·크런치볼 연쇄·목표 반영·낙하·섞기 이벤트를 정해진 순서로 보여줍니다. 잔흔만 남고 논리 보드와 화면 위치가 일치하면 다음 입력을 허용합니다.

한 행동의 다음 상태와 난수 상태는 한 번만 확정합니다. 중간에 앱이 가려지면 조작 중 경로는 취소하고, 이미 확정한 행동은 중복 차감 없이 최종 상태로 복원합니다. 장면을 다시 열었을 때 오래된 콜백이 새 판을 바꾸지 못하도록 세션 ID로 구분하고 예약 작업을 정리합니다.

### 6-3. 재현과 저장

시드·난수 상태·보드·목표·횟수·규칙 버전으로 같은 문제를 재현합니다. 연출용 난수는 보충용 난수와 분리해 파편 수를 바꿔도 다음 볼이 달라지지 않게 합니다.

유효 행동의 최종 논리 상태가 정해지면 연출 전에 한 묶음의 JSON으로 저장합니다. 보드·목표·횟수·난수·행동 ID를 따로 저장하다 일부만 바뀌지 않게 합니다. 앱이 파열 도중 닫혀도 복귀 때 이미 정산한 상태를 복원하고 횟수를 다시 차감하지 않습니다. 설정은 바뀔 때 저장하고 매 프레임 저장하지 않습니다.

저장 형식·게임 규칙·난수 방식의 버전을 함께 기록합니다. 저장 실패 시 메모리의 판은 계속하고 실패를 알립니다. JSON을 읽을 때는 칸 수·색 범위·고유 ID·유한한 숫자·목표·버전을 확인한 뒤 기존 상태를 바꿉니다. TypeScript 타입만으로 외부 JSON이 검증되는 것은 아닙니다. JSON 내보내기를 별도 제공하며 로컬 파일의 브라우저 저장을 영구 보관으로 보장하지 않습니다.

### 6-4. 연결 검사와 섞기를 단순하게 만들기

현재 규칙에서 세 볼의 유효한 길은 가운데 볼 하나와 그에 이웃한 같은 색 볼 둘로 표현할 수 있습니다. 따라서 각 칸에서 같은 색 이웃이 서로 다른 두 개 있는지만 찾으면 됩니다. 전체 경로를 깊이 탐색하는 시스템은 필요하지 않습니다. 범위는 최대56칸×8이웃입니다.

56칸이 모두 차 있고 색이 4개라면 같은 색 볼 3개는 반드시 있습니다. 연결 없는 판의 복구는 그중 3개를 이어진 칸에 놓아 보장할 수 있습니다. 무작정 수십 번 재시도하거나 색을 새로 뽑을 필요가 없습니다. 이 판단은 지금의 완전한 직사각형·빈칸 없음·볼 이동을 막는 장애물 없음·대각선 허용 규칙에 한합니다. 구멍·잠긴 볼·새 색을 추가하면 다시 검토합니다.

## 7. 최적화의 구체적인 순서

### 화면

- 같은 아틀라스와 그리기 방식을 공유해 묶어 그릴 기회를 늘립니다. 아틀라스 하나가 항상 드로콜 하나라는 보장은 없습니다. 레이어·블렌드·필터로 분리되는지 측정합니다.
- 볼·껍질·속·그림자를 꼭 필요한 레이어만 사용합니다. 화면을 크게 덮는 반투명 효과와 풀스크린 블러·굴절은 나중에 비용을 확인합니다.
- 엔진 파티클 풀을 공유하고 활성 파편80개 예산은 화면 전체에 적용합니다. 볼마다80개씩 생성하지 않습니다. 부족하면 새 장식 효과를 줄이고 게임 결과는 생략하지 않습니다.
- 글자·목표는 값이 달라질 때만 갱신합니다. 매 프레임 글자 이미지나 캔버스를 새로 만들지 않습니다.
- 팝업을 열 때마다 텍스처를 만들지 않습니다. 장면 종료 시 Tween·이벤트·음원·임시 텍스처를 정리합니다.
- 내부 해상도는 표시 크기와 분리합니다. 품질 변경은 연결 중에 하지 않고 다음 판 등 안전한 시점에 적용합니다.
- DPR은 Canvas·엔진 양쪽에서 중복으로 곱하지 않습니다. DPR 상한과 함께 내부 픽셀 수 상한도 두어 큰 iPad 화면에서 비용이 커지지 않게 합니다. 첫 상한은 약200만 픽셀 후보이며 선명도를 비교한 뒤 조정합니다.
- 시간 기반 엔진 Tween을 사용합니다. 120Hz 화면에서 동작 속도가 두 배가 되지 않게 하고, 앱 복귀 때 긴 경과 시간을 연출에 한꺼번에 밀어 넣지 않습니다. 확정된 논리 상태로 정리한 뒤 재개합니다.

### 소리

- 확보한 32개는 연구 후보입니다. 첫 플레이에는 약 10개의 역할과 필요한 짧은 변주만 골라 넣습니다. 실제 왁스 녹음은 아직 0개입니다.
- 가까운 파열·속·착지를 별도 가공하고, 원본과 변환 내용을 보존합니다. 말소리·잡음·울림·잘림·반복 피로를 사람이 들어 확인합니다.
- 짧은 효과음은 미리 해독하고 입력할 때 파일을 읽지 않습니다. 모노 변환은 공간감이 불필요한 소리만 비교해 선택합니다.
- 볼마다 껍질·속을 두 겹씩 무조건 재생하지 않습니다. 빠른 파열은 작은 묶음으로 재생하고 마지막 파열·크런치볼·목표 확인음을 우선합니다.
- 음량·재생 수·길이로 겹침을 관리하고 최종 출력의 피크와 청감을 함께 확인합니다. 개별 파일의 피크를 맞췄다고 합친 소리가 안전해지는 것은 아닙니다.
- 첫 시작 버튼에서 오디오를 활성화합니다. 앱 전환 시 중지하고, 복귀 때 필요한 경우 사용자 입력으로 재개합니다. 실제 기기의 음소거·출력 경로·블루투스 지연을 따로 확인합니다.
- Phaser가 관리하는 AudioContext와 음량 경로를 재사용합니다. 별도 Howler나 새 AudioContext를 겹쳐 만들지 않습니다. 동시8개 예산은 껍질·속·UI·특수 효과를 합친 값이며, 소리 실패가 규칙 처리를 멈추지 않게 합니다.
- 음악은 첫 손맛 시제품에서 제외하는 제안입니다. 넣을 때는 긴 곡 전체의 상주 해독 비용과 스트리밍의 차이를 비교합니다.

### 계산과 로딩

- 연결 가능 검사는 행동이 끝날 때 합니다. 각 볼의 같은 색 이웃 둘을 찾는 짧은 검사로 처리하고 매 프레임 전체 경로를 탐색하지 않습니다.
- 새 객체·배열 할당을 무조건 없애기보다, 드래그와 파편 갱신처럼 자주 도는 곳에서 급격한 증가를 먼저 없앱니다.
- 이미지·효과음은 첫 판 전에 준비합니다. 연구 사진·15장 목업·미사용 음원은 불러오지 않습니다.
- Web Worker·GPU 압축·복잡한 셰이더는 계측으로 필요가 확인된 뒤 추가합니다. 56칸 규칙 계산을 처음부터 병렬화하지 않습니다.

## 8. 화면 크기와 접근성

가로세로 비율이 달라도 정사각형 셀과 7×8칸은 유지합니다. 보드 폭과 사용 가능한 높이에서 더 작은 셀 크기를 골라 배치합니다. 상단 목표·하단 여백·안전 영역을 먼저 확보합니다.

iPad의 넓은 화면에서는 보드가 지나치게 커지지 않게 최대 폭을 둡니다. 세로·가로·분할 화면에서도 세로형 게임 영역을 유지합니다. 웹에서 기기 회전을 항상 강제로 막을 수 있다고 가정하지 않습니다.

375×667, 390×844, 768×1024, 820×1180과 가로·분할 크기를 브라우저에서 검사하고 실제 기기에서도 확인합니다. 큰 화면에서 9:16 이미지를 단순 확대해 버튼을 배치하지 않습니다.

색 외 표면 무늬, 선택 테두리, 특수 볼 표식을 함께 씁니다. 움직임 줄이기와 효과음·진동 설정을 둡니다. 진동은 지원되는 기기에서만 켭니다. 메뉴는 키보드와 화면 읽기 도구로 접근할 수 있게 합니다. 퍼즐 보드 전체의 화면 읽기 조작은 별도 설계·검증이 필요한 범위로 남깁니다.

## 10. 반드시 할 검사와 기록

### 규칙 검사

대각선·색 불일치·볼 재사용·한 칸 되짚기·2개 취소·입력 끊김·유효 행동 중복 실행을 검사합니다. 6개 생성 위치, 특수 볼 포함 시 생성 금지, 모서리 3×3, 겹친 연쇄, 각 목표 중복 방지도 확인합니다.

마지막 행동으로 목표 달성·횟수 0의 성공 우선, 낙하 뒤 자동 소거 없음, 연결 없는 판의 무료 섞기와 재검사도 검사합니다. 고정 보드와 시드로 결과를 비교하고, 빈칸·볼 개수·음수 횟수·중복 ID가 남지 않는지 확인합니다.

### 기기·성능 검사

- 평범한 3개, 긴 연결, 여러 크런치볼 연쇄, 판 전체 낙하, 팝업 열기에서 각각 측정합니다.
- 워밍업 뒤 같은 시나리오를 3회 이상 반복합니다. 기기·OS·브라우저·빌드·해상도·품질·측정 시간을 함께 남깁니다.
- 평균 fps만 보지 않고 프레임 간격의 p95·p99, 긴 멈춤, 입력 지연, 드로콜·활성 파편·텍스처 계산량·음원 버퍼·리스너 수를 봅니다.
- CPU 시간과 GPU 시간을 구별합니다. 지원되지 않는 GPU 시간·전체 탭 메모리는 미측정으로 씁니다. 발열·배터리는 장시간 실기기 관찰 전 수치로 보장하지 않습니다.
- 20판 반복, 다시 시작, 지도 왕복, 앱 전환, 오디오 재개, 화면 크기 변경, WebGL 복구를 확인합니다. 복구가 어려우면 안전한 재시작 안내를 제공합니다.
- Playwright의 WebKit 검사는 Safari에 가까운 자동 검사이며 실제 iPad Safari 시험을 대신하지 않습니다. 오디오 해독·재생 이벤트 성공도 사람의 청음과 구분합니다.
- 단일 HTML은 네트워크 요청 없이 그림·소리가 동작하는지 따로 확인합니다. iPad 파일 앱 미리보기와 Safari 실행은 다를 수 있어 실제 여는 경로도 기록합니다.

### 손맛·음향 검사

5~8명 정도의 초기 관찰로 3개와 6개의 차이, 크런치볼 예측, 목표 이해, 반응 지연과 기다림을 찾습니다. 통계적인 장기 재미 검증으로 쓰지 않습니다. 같은 보드에서 연출만 바꾸고 경험 순서를 바꿔 비교합니다.

파열 소리는 이어폰·휴대폰 스피커·iPad에서 직접 듣습니다. 파일 해독 성공, 파형 검사, 브라우저 재생, 사람의 청음, 실기기 플레이를 각각 구분해 `30_검증결과.md`에 기록합니다.
